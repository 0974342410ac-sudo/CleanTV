# XGIMI RS10 projector, China market (device m7642, MediaTek, build tree MTK958C_CODE, product Product_kirinultra),
# Android 9 (SDK 28, PPR2.180905.006.A1), GMUI/INUI 6.4.200.03, firmware XGIMI_PIGCHIVALROUS_XM13M built 2024-07-02.
# Notes only so far: read from the USB upgrade file, not from a running unit. No removal list yet.
#
# Firmware file (2026-10-23): a plain MStar/MediaTek USB upgrade bin, not encrypted (unlike the DOHKO's
# XGIMI_HORSEPOPULAR_*.bin). It starts with the mboot script: "# File Partition: <name>" then
# `filepartload <addr> $(UpgradeImage) <offset> <size>`; system (11 pieces) and vendor (19 pieces) are Android
# sparse images, ext4 inside, readable with 7-Zip. vbmeta_a is created but never written by the script.
# Locales: AOSP apps ship without any vi (and mostly without en) resources; XGIMI apps have Chinese as the default
# text. Switching the system language to Vietnamese changes nothing by itself.
# Home is com.xgimi.home (vendor/priv-app/XgimiHome_release838); keyboard com.sohu.inputmethod.sogou.tv (Sogou).
#
# Vietnamese: tools\xgimi-vi\rs10-overlays.ps1 builds 41 overlay APKs (dist\rs10-vi, 4,914 strings: Settings,
# home, systemui, player, cast, upgrade, shutdown...) from rs10-apps-chuoi.tsv and the Chinese->Vietnamese tables;
# tools\xgimi-vi\rs10-install.ps1 -TvHost <ip> installs and enables them (-Remove undoes). Android 9 has no
# `cmd overlay fabricate`; non-static overlays from /data can still be enabled by the shell there. Not yet tried
# on a real unit: check that `cmd overlay list` shows [x] and that the Settings text changes.
# Not translated: Sogou keyboard (use Gboard), factory menus, Chinese TTS, data reporter, string arrays,
# feature-config JSON strings ([{key:...}]) and Android's autofill patterns.
#
# XGIMI H6 (2026-10-23): firmware XGIMI_PIGCHIVALROUS_XM03D built 2024-02-29, same platform (m7642, Android 9,
# product Product_xiaobai, GMUI 6.0.400.07), same plain bin layout. Its strings are in h6-apps-chuoi.tsv;
# rs10-overlays.ps1 -Device rs10 builds one overlay set for both (43 APKs, 5,039 strings), and the USB updater's
# m7642 profile installs it on either. Not yet tried on a real H6.
#
# How ADB gets switched on, read from firmware XGIMI_PIGCHIVALROUS_XM13M.bin (m7642, Android 9, user build), 2026-10-25:
# - vendor/build.prop has service.adb.tcp.port=5555, persist.adb.tcp.port=5555, ro.adb.secure=0 (no key prompt),
#   but also persist.sys.usb.config=mtp, and adbd only starts when sys.usb.config contains adb.
# - vendor/etc/init/hw/init.m7642.usb.rc: "on property:persist.sys.usb.config=mtp,adb" sets it straight back to mtp,
#   so Android's USB debugging switch (mtp,adb) is undone; "persist.sys.usb.config=*" copies the value into
#   sys.usb.config, so only a plain "adb" value starts adbd. Nothing in the firmware writes that value.
# - No AOSP Settings / TvSettings in the image: XGIMI's com.android.newsettings has no developer or ADB entry.
# - Factory menu (com.xgimi.minitvfactory, action com.xgimi.action.factoryMenu): in XGIMI Settings, on the device
#   info page (sysInfo.device_info_state.page4), hold the remote's Up key until it repeats 20 times. Its ADB on/off
#   item ("adb" 开/关, start/stop adbd) lives in SecondMenuActivity, which nothing in the app opens.
# - XgimiManager's Baidu tvsafe AdbSwitch rewrites adb_enabled at boot only once its "adbservice" flag was set
#   (off by default). com.xgimi.remote (XgimiRemoteDebug) starts an sshd for XGIMI's own key (remote support).
# So on this firmware ADB comes only from XGIMI (remote support) or from a changed vendor/build.prop
# (persist.sys.usb.config=adb) flashed with the USB upgrade.
#

# REAL-DEVICE TEST (2026-10-28, v6.8.x m7642, screen recording): the installed-overlay method does NOT work on a
# stock retail unit. Every rs10-vi overlay fails at install with
#   Failure [INSTALL_FAILED_INTERNAL_ERROR: ... Overlay vn.cleantv.overlay.rs10.<app> must be signed with the
#   platform certificate.]
# Android 9 refuses to install an RRO that targets a system/XGIMI app unless the overlay APK is signed with the
# device's platform key (or the target app's key); ours is debug-signed and non-static, so 0/41 install. This
# retracts the earlier guess ("non-static overlays from /data can still be enabled by the shell there") -- it is
# false on retail builds. The firmware is a user build (no adb root, id -u = 2000), so the overlays also cannot be
# pushed to a trusted overlay partition (/vendor|/product/overlay) nor fabricated (no `cmd overlay fabricate` on
# Android 9). Launcher/Home replacement and debloat still work; only "3/3 Viet hoa Cai dat XGIMI" is impossible
# over ADB. The updater now detects this one cause and prints a single plain Vietnamese line instead of ~41 red
# INSTALL_FAILED lines (installOverlays, UpdaterActivity). Full system Vietnamese needs the overlays baked into the
# firmware image as static overlays in /product/overlay, flashed with the USB upgrade -- to be built and flash-
# tested when a real m7642 unit is available (none online at the time of this test).
